# Outcome Controller Hook

## Purpose
The outcome controller hook bridges the `OutcomeController` service and OpenCode lifecycle hooks. It manages cache-safe volatile checkpoint dispatch nudges, enforces Manager correlation on native `task` calls, tracks tool observations, and captures external user turn receipts.

## Key Components
- `createOutcomeControllerHook`: Factory creating the hook object.
- `OUTCOME_CONTROLLER_METADATA_KEY`: Metadata key (`oh-my-opencode-slim:outcome-controller`) for volatile trailing dispatch nudges.
- `experimental.chat.messages.transform`: Strips previously injected outcome nudges and appends at most one trailing volatile dispatch message when an active claimed checkpoint exists.
- `tool.execute.before`: Enforces exact single OMOS dispatch marker correlation when `task` is called with `subagent_type='outcome-manager'`, marking the checkpoint as `dispatching`. Observes ordinary tool executions, allowing post-accept ordinary tool calls without mutating predecessor or intake, and fences pending tool calls by exact rootSessionId, outcome ID, and generation, skipping persistence if identity cannot be established.
- `reserveManagerDispatch` / `failReservedManagerDispatch`: Brackets the combined plugin preflight so any later hook rejection retires a reserved Manager claim before native launch.
- `tool.execute.after`: Binds the Manager task ID and generation upon task tool return, captures tool output digests, and prevents stale callbacks from mutating successor generations by verifying exact rootSessionId, outcome ID, and generation identity before persistence.
- `chat.message`: Observes external user turns with whole-message external provenance (rejecting the entire message if any authoritative part is synthetic, internal initiator, compaction continuation, or carries internal metadata; prefers output.parts over cleaner input.parts; requires host message ID and treats duplicate host events idempotently; projects attachment-only messages into bounded deterministic stable representations without circular/volatile fields) and records `external_user` receipts in the durable outcome store or post-accept pending intake.
- `event`: Evaluates managed idle liveness after child-running suppression, reconciles same-epoch operations as before, suppresses valid waits and accepted outcomes, and shares the process-global owner-safe two-attempt budget with periodic/stopped-child/restart wakes. SDK failures debit; duplicate busy/idle/retry/error delivery does not rearm. Exhaustion still allows event-driven telemetry observation.
- `notice-state.ts`: static non-authorizing label; meaningful fingerprint excludes normalized read/status operation AND controller-observed receipt churn. Recovery transforms suppress after two distinct completed narration-only turns for the same cause. Host history scanning crosses newly persisted incomplete assistants/internal wakes, not external/tool-bearing boundaries. Duplicate transforms do not count; missing telemetry cannot reopen suppressed causes (before exhaustion, notices remain). Valid dispatch capabilities remain available with unchanged bytes; suppression has no governance authority.
- Idle admission: paired idle notifications share one cycle even across SDK acknowledgement. Losing to a periodic read owner registers a deduplicated, disposal-safe release waiter and rechecks eligibility. Restart success blocks restart prompts only; genuine rearm can admit later Controller prompts.
- `../external-message.ts`: shared whole-message external provenance predicate used by both hooks; authoritative output parts including empty arrays, mixed synthetic/internal/providerMetadata/compaction rejection. Distinct external IDs rearm only liveness, not governance; receipt authority is unchanged.
- Managed-root Bash guard: Rejects literal current-PID termination and explicit OpenCode process/service restart forms before tool observation, directing the orchestrator to `external_handoff`; aliases, scripts, pipelines, and obfuscated forms are intentionally outside scope.
